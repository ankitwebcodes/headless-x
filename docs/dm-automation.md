# DM automation

DM-only implementation; composer, posting, auth and local browser workers are unchanged.

## Deploy

- Keep the existing `DATABASE_URL` and `AUTH_SECRET`. DM accounts and checkpoints are stored in a new `dm_documents` table, created idempotently by this module, matching the existing DM initialization pattern. No existing posting tables are changed. The equivalent schema is in `lib/dm-migration.sql` for environments that provision tables separately.
- `DM_ENCRYPTION_KEY` is optional; otherwise `AUTH_SECRET` derives the AES-256-GCM key. Keep the chosen secret stable and backed up. Rotating it without re-encrypting account records makes existing cookies unreadable.
- Set a random `DM_WORKER_KEY` to enable authenticated cloud dispatch. On Netlify, the DM-only `netlify/functions/dm-tick.mjs` schedule invokes `/api/dm/worker` once per minute. Set `DM_PANEL_URL=https://repostops.xyz` if Netlify's `URL` is not the desired public origin. Other hosts can schedule a POST to that endpoint with `Authorization: Bearer <DM_WORKER_KEY>`. Without a scheduler, the open DM page advances saved runs; closing it pauses further dispatch until it is reopened.
- Existing `DM_INGEST_KEY` works when `DM_INGEST_OWNER_ID` identifies its panel user, or there is exactly one administrator in Postgres. For multiple users, use **Pair cookie extension** in the DM page: it issues an owner-scoped key valid for 30 days. Replace the extension's key, not its runtime behavior.
- An administrator can click **Import existing DM accounts** to copy and verify legacy global sessions into their owner-scoped encrypted store. Imports are idempotent; the source remains recoverable. Expired cookies must be refreshed. Large imports can be repeated if the request budget is reached.

## Workflow

1. Select or add up to 12 accounts. Every cookie save verifies X's identity. A different account cannot overwrite an existing account. Cookie refreshes deduplicate by X user ID.
2. **Scan inbox** starts a snapshot. **Refresh from top** starts from the latest inbox page; **Continue older chats** explicitly resumes the trusted inbox and preserves partial results after rate limits; **Refresh inbox** starts a new snapshot after completion. Every page checkpoints chats and cursors together. Results and run targets sort by X conversation sort timestamp and precise event ID, newest first. Cursor advancement must move toward older entries. Parallel waves start in that order; completion within a wave can differ. Counts are discovered totals until scanning finishes. Unread uses X's read receipt IDs, compared as integers without losing snowflake precision; it does not mean merely that the last message is incoming. Refresh inbox once after upgrading older scan results to load read status and outgoing-message timestamps.
3. Enter the custom reply, choose **All**, **Unread**, or **Inactive**, then Start. All processes the latest incoming message in matching conversations, Unread requires unread incoming messages, and Inactive covers regular inbox chats with no activity for 24 hours. Message requests and low-quality/untrusted conversations are excluded in every mode, explicit selection, cached scan, and live pre-send check. The untrusted timeline is never paginated. Search, result filters and explicit selection narrow targets further. Settings and the reply template save separately for each account, including when switching accounts immediately after an edit. All targets come from that account's stored scan; client metadata cannot choose another account's inbox.
4. The default **Chat cooldown** is two hours. Choose Off, 30 minutes, or 1, 2, 4, 6, 12 or 24 hours. Cooldown applies to every mode and explicit selection, and includes both manual and automated outgoing replies, even if a newer incoming message arrives. The server combines confirmed local send times with live conversation history, walks up to eight history pages to verify the window, and rechecks before every write. An unverifiable window retries without any repost or reply. Cooldown rows show their remaining wait and are skipped for the current pass; they do not automatically send when the timer expires. Start a new pass afterward. Confirmed incoming entries remain deduplicated even with cooldown Off.
5. No readable message or no resolvable X post produces an explicit skip/error. Structured tweet attachments, URL entities, cards containing X status links, and status URLs in text resolve to post IDs. Standalone media or external links without an X post are not repostable. Matching the supplied v8.1 extension, the worker selects the latest received post link/card across the available message history, even if newer incoming text has no post. Only the outer shared post is targeted; embedded author-profile and quoted-post URLs are excluded. Unexpanded X short links resolve without account cookies and cannot silently become successful skips.

   The worker always creates a fresh repost. If the post is already reposted, it calls `DeleteRetweet` with `source_tweet_id`, verifies the absent state, calls `CreateRetweet`, then verifies the present state. Same-account refreshes of the same post are serialized. Both mutation operations resolve before undoing; a batch with insufficient time defers before touching the existing repost. Replies require a recorded fresh mutation ID/time and read-back confirmation for the exact post and cookie session. HTTP success, a mutation ID, or X code 327 alone cannot mark success. Unverifiable writes stop before the DM. Saved repost checkpoints are rechecked when resuming. It selects the latest received post/card, including in outgoing-last conversations once cooldown has expired; there is no separate include-replied toggle.
6. Runs persist their frozen template, targets, stage, request IDs, repost successes and replies. Incoming entry IDs deduplicate across later runs. Failed sends resume after the repost checkpoint. Account leases coordinate scans, page dispatch and scheduler requests. The default 2× speed doubles each wave from two to four chats (maximum six with the advanced base setting at three). 1× retains standard concurrency. Wave delay and rate-limit backoff remain in force, so actual throughput depends on X and database latency. Scan page gaps default to 300ms instead of 600ms.
7. HTTP 429/code 88 pauses the account until retry/reset deadlines (at least 60 seconds). Transient read failures back off; auth/restriction failures require operator attention. A timeout or missing acknowledgement after a write is uncertain and is never blindly resent through another transport. A parallel request already in flight may finish after another request observes a rate limit or pause.
8. Pause is persisted. Already-issued requests can finish; new writes check the saved status. Stop completes the run without issuing remaining work. Cooldown can be adjusted while paused; message, mode and pacing stay frozen for that run.
9. For uncertain writes, inspect the linked chat first. **Confirmed sent** records completion; **Not sent · allow retry** clears the ambiguity and pauses the run for an explicit Resume. Automatic retry never clears uncertainty.
10. The six cards above the workspace show Total chats, Done, Reposted, DMs sent, Cooldown and Failed. Each row has independent Repost, DM reply and Result columns; green Done requires both a read-back-verified repost and a confirmed reply. Older acknowledgement-only or read-only markers show Unverified or Already present · refresh needed, and never inherit a fresh-action green check. Repairing such a repost preserves a previously confirmed reply without sending another DM. **Verify saved reposts** checks up to 12 saved chats per pass, updates verification metadata, and never reposts or sends a DM. Already-confirmed replies stay deduplicated. Post links and verification timestamps make the result inspectable. The per-chat history survives a reload, a fresh scan and later runs. New incoming entry IDs reset completion checkmarks while preserving conversation-wide cooldown. GET polling continues during a running batch. Preview mode is under Advanced options and never receives completion checkmarks. Account connection and diagnostics live in the settings drawer; a masked four-digit X Chat passcode can be saved when connecting an account or through Save account details. Passcodes remain encrypted with cookies, are never returned by the session API, and support explicit removal. Cookie refresh preserves them. This is secure storage, not an implemented X Chat unlock path.

## Multiple accounts and clearing history

The panel dispatches an independent bounded batch for every started account, up to 12, and polls the selected account separately. Switching the visible account does not cancel another account’s batch or stop later batches. Account chips show each run’s status and X restriction reason. A code 226 restriction pauses only that account and stays blocked until the operator resolves it with X; Start all skips restricted/auth-failed accounts. Other accounts continue. **Start all ready accounts** uses each account’s saved reply, mode, speed and cooldown; it skips missing scans/templates, completed or cooling-down chats, and started/paused accounts. Pauses and rate limits remain per account. While the panel is closed, dispatch requires the cloud scheduler described above.

Under **Account settings → Start fresh**, choose the current account or **All connected accounts**, then **Preview clear before today**. The cutoff is midnight in the browser’s displayed timezone. Confirmation deletes eligible scans, chat markers, processed-entry ledgers, finished runs and their latest pointers from before that cutoff. Today’s records, cookies, templates, settings, leases and unresolved writes survive. Clearing completed-entry history intentionally allows those incoming messages to be processed again on a new scan; live manual/automated-message cooldown still applies.

Cleanup refuses accounts with started or paused runs, or an active account lease. It holds all affected leases before deletion and compares record versions, so changed records survive. The confirmation recalculates the plan on the server; the preview itself deletes nothing. No database migration is needed.

## Removing an account

Select an account, open **Account settings**, then click **Remove account**. A native confirmation popup names the account and explains that its automation, stored cookies and Chat passcode will be removed. Cancel makes no deletion request. The DELETE route also requires explicit confirmation and owner-scoped account access.

Confirmed removal stops that account’s active/paused runs, waits for its in-flight lease before removing credentials, and leaves other accounts and their runs alone. X rate-limit cooldown does not prevent disconnecting. Scan/history records remain available for reconnection and duplicate protection. Removing the last account disables automatic legacy adoption so a later refresh cannot recreate it; explicit legacy import still remains available.

## Local access

Use `http://localhost:3000/dm` after starting the built panel. A single Next server should own port 3000 for both IPv4 and IPv6; separate listeners can serve different builds for `localhost` and `127.0.0.1`. After an upgrade, hard refresh to replace cached page chunks. A single legacy DM account is automatically adopted only for its configured owner or the sole administrator; other installations keep the explicit import button.

## X endpoints and limits

The adapter uses cookie-authenticated X web endpoints. Repost discovery prioritizes the main client bundle, excludes vendor/i18n downloads, and shares discovery across concurrent requests. Missing operations retry after a short cooldown instead of poisoning the cache for 30 minutes. Fresh reposts use the discovered `DeleteRetweet` (when already present) and `CreateRetweet` GraphQL mutations with `variables: { tweet_id }` and `features: {}`. The previous payload, which included `dark_request` and omitted `features`, returned 404 in the live test; the current client shape succeeded. X error 327 cannot establish a newly created repost and does not allow the reply to proceed. The retired REST repost URL is not used. An unavailable repost transport pauses the run instead of failing the entire inbox.

DM sending uses `POST /i/api/1.1/dm/new2.json` with a flat JSON body containing `conversation_id`, `text`, and the stable `request_id`; it does not use the nonexistent conversation-specific `send_message.json` route. The form fallback is limited to explicit request-format rejection. Both steps were validated in one explicitly approved chat: X confirmed already-reposted status, acknowledged the reply with a message ID, and a read-only history fetch verified the sender, ID and exact text. No other chat was processed in that validation.

`DM_QID_CREATERETWEET`, `DM_QID_DELETERETWEET`, `DM_QID_TWEETRESULTBYRESTID` and `DM_QID_VIEWER` can supply verified operation IDs if bundle extraction cannot find them. These private web contracts can change; errors are surfaced, never treated as a successful repost/reply just because HTTP returned 200.

Encrypted X Chat is **not implemented by setting headers**. Optional per-account unlock codes are encrypted at rest, but encrypted threads remain explicitly locked. The documented Chat XDK needs key recovery, verified sender/conversation keys, cryptographic operations, and HTTP transport authentication. Its documented API transport uses OAuth user tokens; a cookie-only equivalent has not been verified here. No unlock-code guessing or fake decryption is attempted. The supplied `super-x-extension-v8.1.zip` was inspected as reference data. Its latest-received-link selection and undo-then-repost behavior are now represented server-side; its browser-dependent encrypted Chat access is not replicated by storing a passcode.

## Verification

### Post failures versus account stops

An empty HTTP 404 from a repost mutation is not proof that a post was deleted or that an account is restricted. The engine refreshes operation discovery (throttled across concurrent lookups), keeps that chat's reply blocked, and retries the post in at most three attempts. Other chats remain eligible. Exhausted posts stay failed and retain their diagnostic; they never become successful or skipped without confirmation. Explicit unavailable-post responses still skip that chat. Authentication failures, X restriction codes 226/326/344, and rate limits keep their account-wide stop/backoff behavior. The mobile fleet displays the full account error or Start-all skip reason. The DM total explicitly identifies older replies without fresh repost proof.

### Running continuously on a Windows PC

Run `powershell -NoProfile -File scripts/start-dm-worker.ps1` once from the project. Pass `-NodePath` with the absolute Node executable if Node is not on PATH. Keep the PC awake, its internet connection available, and both the panel server and this worker running. The supervisor restarts a crashed worker. It advances up to 12 eligible runs concurrently without depending on an open phone/browser tab; it does not start new runs or resume paused/restricted accounts. The fleet label reflects a recent worker heartbeat, not merely the presence of an environment key. X account restrictions and daily limits still apply; code 344 stops only the affected account. No automatic retry bypasses an X restriction.

An operator Stop now preserves cancellation when an in-flight batch finishes reading. Batch-time deferrals do not consume the repost failure retry allowance. Deleted/unavailable posts skip the reply and retain their reason.
